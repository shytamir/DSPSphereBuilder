# Version promotion and change records

## Authority and scope

This is the authoritative procedure for manually promoting [VERSION](../VERSION),
identifying builds and maintaining release change records. It also applies to
publishing a hotfix without changing major/minor. [PROJECT.md](PROJECT.md) remains
the sole authority for current scope, owner decisions, nominated candidates,
validation, acceptance and publication. [BUILD.md](BUILD.md) owns build commands
and package mechanics; it does not grant promotion authority.

Only the owner authorizes a manual major/minor promotion and its target. Planning,
implementation permission, a passing build or candidate acceptance alone does not
authorize a different VERSION value. An explicit instruction such as promoting an
accepted candidate to a named version is sufficient for that promotion; do not
request the same permission again. Record the instruction, target and scope in
PROJECT.md. Publication is a separate owner action unless explicitly delegated.

This procedure preserves the implemented version scheme. Changing that scheme,
the plugin GUID or package identity is a separate decision, not a routine bump.

## Version fields

Let `M` and `m` be the manually authored major/minor values, `N` the existing
workflow's `github.run_number`, and `h` the first seven hexadecimal characters of
the source commit. Do not use the examples below as proposed next versions.

| Surface | Value | Purpose |
| --- | --- | --- |
| DLL assembly name / BepInEx GUID | `DSPSphereBuilder` / `dsp.spherebuilder` | Stable identity across ordinary updates |
| DLL `AssemblyVersion` | `M.m.0.0` | Assembly identity for this major/minor line |
| DLL `AssemblyFileVersion` and PE file version | `M.m.0.0` | Existing four-component file metadata; not a unique build identifier |
| DLL `BepInPlugin.Version` | `M.m.N` | Loader-visible version; must equal the package version |
| Thunderstore `manifest.json` version | `M.m.N` | Public numeric version; package file is `DSPSphereBuilder-M.m.N.zip` |
| DLL `AssemblyInformationalVersion` and internal `BuildInfo.Label` | `M.m.N.h` | Diagnostic build label with source revision |
| Internal build record | Full commit, run ID, `N`, attempt, dirty state, package/DLL SHA-256 | Exact source, execution and byte identity |

For example, major 1, minor 2, build 84 and commit prefix `abcdef0` produce
package/loader `1.2.84`, assembly/file `1.2.0.0`, and diagnostic label
`1.2.84.abcdef0`. Hashes never enter numeric package, loader or assembly versions.
The diagnostic label is not a SemVer package version. File version alone cannot
distinguish builds within a major/minor line; use the informational version and
build record rather than silently changing its established mapping.

These fields are generated by [Get-BuildIdentity.ps1](../scripts/Get-BuildIdentity.ps1)
and [Build-Plugin.ps1](../scripts/Build-Plugin.ps1). Do not hand-edit generated
BuildInfo, DLL attributes, a built manifest, archive name or accepted ZIP to
simulate a promotion. .NET distinguishes assembly, file and informational versions;
see [Microsoft's versioning guidance](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/versioning).
The table above is this project's mapping, not a claim that all three serve the
same purpose or uniquely identify the same build.

VERSION contains only `MAJOR=<integer>` and `MINOR=<integer>`, with non-negative
decimal values and no leading zeros. There is no manually maintained patch,
hash, date or prerelease suffix. Respect compiler/loader numeric limits; validate
the actual resulting metadata instead of assuming any parser-accepted integer
will compile.

The package uses Thunderstore's three-number version format; its third component
is a sequential build number, not a count of fixes. Compare versions as integer
tuples, never as decimals or text. A proposed upload must be newer than the
highest published package, not merely the last one uploaded.
[Thunderstore's rules](https://wiki.thunderstore.io/mods/creating-a-package#version-number)
describe this ordering and update mechanism.

New workflow runs consume new numbers, including non-release and failed runs;
gaps are normal. A rerun retains `N` and increments its attempt. Major/minor
promotion does not reset the workflow sequence. Keep run ID, number and attempt
distinct, as specified by [GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/variables).
Local rehearsal numbers do not reserve public versions. A CI build is not itself
an accepted candidate or release.

## Choosing a promotion

Recommend the smallest change consistent with the delivered scope; the owner
chooses the actual target:

| Change | Normal treatment |
| --- | --- |
| Fix within the existing product contract | Leave VERSION unchanged; a new CI run supplies a newer third component |
| Compatible new or expanded feature | Propose a minor promotion |
| Deliberately incompatible behavior, supported-data contract or feature removal | Propose a major promotion and normally reset minor to zero; document the impact |
| Documentation, build housekeeping or internal refactoring without product change | No automatic major/minor promotion and no invented feature entry |

Do not infer compatibility from version numbers. Review actual save/continuation,
installation and dependency consequences of the change. Record demonstrated
upgrade or downgrade limits; investigate relevant unknowns before claiming
support. This is a focused comparison with the published baseline, not a new
full-game compatibility programme.

## Change records

### Repository CHANGELOG.md

[CHANGELOG.md](../CHANGELOG.md) is the internal feature history, newest first.
Keep an `Unreleased` section for implemented changes not yet published. Use
`Added`, `Changed` and `Removed` categories where applicable; fixes to an existing
feature belong under `Changed`. Omit empty categories. Log every feature addition,
behavioral change and removal, including relevant user-visible fixes. Describe
the final outcome and important compatibility consequences concisely.

Each item links to the implementation commit or commits that delivered it, using
immutable GitHub commit URLs. An issue, roadmap story or documentation-only
commit is not a substitute for those links. Once the implementation commit
exists, add its link in the next documentation commit, before selecting the
candidate. Do not amend history to make a commit refer to its own hash. Consolidate
follow-up commits into the same feature entry when they implement one outcome.

This is not a copy of `git log`: routine builds, whitespace, management updates
and version-only promotions are not features. Do not backfill unverifiable
history or attribute unshipped features to a release. For a release with no new
feature changes, record that fact without inventing Added/Changed/Removed items.

After verified publication, move only the changes included in that artifact
from `Unreleased` to a heading with the full package version and publication date.
Link the release and retain the implementation links. Leave later or omitted
work under `Unreleased`. Historical release headings record shipped content;
candidate readiness and owner acceptance stay in PROJECT.md. Keep published
entries intact except for factual corrections, explained alongside the correction.

### Thunderstore README Changes

[packaging/README.md](../packaging/README.md) is the source of the installed
package's README, distinct from the repository README. Its final authored
section is `## Changes`: a short player-facing summary of the changes included
since the previous published version. Replace that summary for the next release;
the full history stays in CHANGELOG.md.

Use a few short sentences about what improved or changed for the player. Omit
commit IDs, story numbers, implementation details, formulas, test results and
management status. Mention an upgrade action or limitation only when the player
needs it. Do not announce unimplemented work or claim a pending change has been
published. Avoid a hard-coded future build number; the manifest identifies the
package containing the prose. The builder's required source link may follow the
last authored section; preserve attribution and source access.

Prepare both records before building the candidate. Check that they describe
the same included changes at their different levels of detail. A later README
edit does not alter a ZIP already under owner validation; if it must ship, build
and verify a new candidate rather than modifying accepted bytes in place.

## Promotion workflow

1. **Establish the baseline and authority.** Read PROJECT.md, the published release
   record, VERSION and Git status. Verify current remote package/version and tag
   state. Identify the exact accepted source/candidate and proposed delta. Record
   the owner's authorized major/minor target, or that this hotfix retains it.
   Preserve unrelated changes and any candidate still being validated.
2. **Prepare source and change records.** Complete the authorized implementation
   and affected checks. Review the difference from the published source, update
   both change records and capture any relevant upgrade/downgrade limits. When
   authorized, edit only the two VERSION inputs for the chosen promotion. Do not
   bundle identity, dependency or unrelated code changes into a version-only
   promotion.
3. **Commit and build.** Review and commit the intended promotion inputs with
   their PROJECT update; push under the execution authorization. Use the existing
   workflow and its actual assigned number. Follow [BUILD.md](BUILD.md) for local
   checks and real-reference comparison when runtime source or references changed.
   Do not guess the next CI number or add a new version counter.
4. **Identify and validate the resulting artifact.** Read the matching build
   record; verify source revision, clean state, run/attempt, numeric versions and
   all DLL fields above. Independently download and validate the package and its
   DLL hash, required contents, change prose, licenses and accessible exact source.
   Confirm its numeric version is newer than every published package. Preserve
   the ZIP and build record outside expiring CI storage for the owner handoff.
5. **Record acceptance of the concrete candidate.** PROJECT.md identifies the
   exact artifact, hashes, evidence and owner disposition. A version-only promotion
   of an accepted implementation needs the new metadata/package checked; it does
   not automatically require another gameplay session. Reuse applicable evidence
   explicitly and run a focused recheck only for changed behavior or a concrete
   unresolved concern. Do not infer acceptance of new behavior from an earlier
   candidate or from passing CI. A later build does not supersede the nominated
   candidate without a recorded decision. For an owner-requested version-only
   promotion, link the existing acceptance and promotion instruction to the newly
   verified artifact; do not require a second approval for the same instruction.
6. **Publish and reconcile.** The owner publishes the verified bytes manually.
   Prefer a new GitHub release tag named with the full package version and pointing
   to the candidate source commit; preserve historical tag names and targets.
   Verify the resulting public package/release identity and digest where available,
   then record URLs, version, source/tag relationship and publication evidence in
   PROJECT.md. Finalize the root changelog's release section and move only shipped
   entries. A documentation closeout commit is not a replacement binary.

Keep candidate source, promotion commit, release tag and management closeout
commit distinguishable when they differ. Record observed publication separately
from owner-reported installation results. Neither local package validation nor
acceptance guarantees marketplace moderation or publication success.

## Rejected candidates and rollback

If checks fail, diagnose and fix the affected input before rebuilding, following
AGENTS.md's retry rule. A corrected source commit receives a new workflow run and
version; do not decrement VERSION or reset the sequence to fill a gap. A retry of
the same run can replace its CI artifact, so recheck the matching attempt and
hashes before using it. Preserve accepted or published bytes before any retry.

Never overwrite a published ZIP with different bytes under the same version,
move an existing release tag, or amend release history to hide a regression.
Retain the prior known-good package and its evidence. An owner-directed rollback
must account for any save/layout changes made by the newer build; do not promise
that an older plugin can continue newer data without checking. For a corrective
public update, restore the necessary behavior in source and publish a newly
validated higher version with an honest Changed entry. Owner authority and the
same acceptance/publication boundary still apply.
